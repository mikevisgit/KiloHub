# Kilo Hub — исследование существующих решений перед разработкой

## Контекст

Мы проектируем **Kilo Hub / Vibe Worker Hub** — расширение для VS Code, которое должно дать единое представление обо всей прошлой работе пользователя с Kilo Code.

Основная пользовательская проблема:

> «Я помню, что мы этим занимались, но не помню, в какой папке/проекте и в каком диалоге. Хочу быстро найти это и продолжить работу».

Первоначальная концепция предполагала собственные:
- реестр проектов;
- индексатор истории Kilo;
- суммаризацию по проектам;
- поиск;
- локальный API;
- Kilo plugin/tools;
- позже — semantic search через embeddings.

После поиска существующих решений выяснилось, что значительная часть нижнего уровня уже реализована в других продуктах и частично в самом Kilo. Поэтому перед разработкой нужно сначала исследовать, что можно переиспользовать.

---

# Что уже существует

## 1. Chat Wizard

Проект: **Chat Wizard**

Репозиторий:
https://github.com/Veverke/ChatWizard

Что умеет:
- агрегировать локальную историю AI-диалогов;
- работать сразу с несколькими coding agents;
- искать по истории across workspaces;
- показывать полные диалоги;
- показывать prompt history и timeline;
- возвращать старые сессии обратно в контекст;
- работать локально;
- читать историю в read-only режиме.

Почему важно для нас:

Chat Wizard уже решает значительную часть проблемы:

> «Я помню, что мы это обсуждали, но не помню, где».

Но его основная сущность — **разговор / session**, а не **проект как рабочая единица**.

Для Kilo Hub потенциально можно переиспользовать:
- способы обнаружения истории;
- структуру индекса;
- поиск;
- привязку conversation → workspace;
- UX просмотра истории;
- подход к локальной работе без отдельного backend.

---

## 2. Callimachus

Проект: **Callimachus — AI history search**

Что особенно интересно:
- поддерживает Kilo Code и другие coding agents;
- использует локальный индекс;
- VS Code extension выступает как клиент;
- тот же индекс используется другими интерфейсами;
- архитектура разделяет данные/индекс и UI;
- есть CLI/MCP-подход к тем же данным.

Почему это важно:

Это очень близко к нашей архитектурной гипотезе:

**локальный индекс → API/CLI → несколько клиентов**

То есть не нужно запихивать всю логику внутрь VS Code extension.

Нужно изучить:
- как устроен индекс;
- кто отвечает за обновление;
- как представлены workspace и sessions;
- есть ли стабильный API;
- как устроен MCP;
- можно ли переиспользовать или адаптировать их архитектуру.

---

## 3. Project Manager for VS Code

Проект:
https://github.com/alefragnani/vscode-project-manager

Что умеет:
- хранить глобальный список проектов;
- автоматически находить проекты;
- показывать проекты в sidebar;
- открывать проект в текущем или новом окне;
- поддерживать теги;
- работать как глобальный project switcher.

Почему важно:

Механизм «реестр проектов + открыть одним кликом» уже давно решён.

Не нужно автоматически считать, что нам обязательно нужен собственный discovery проектов.

Нужно посмотреть:
- как они получают список известных проектов;
- как хранят метаданные;
- как открывают workspace;
- можно ли часть механизма переиспользовать;
- достаточно ли встроенных VS Code API.

## 4. Projects Dashboard — Sidebar

Расширение: **Projects Dashboard — Sidebar**

Что умеет:
- единый список проектов;
- recently opened folders;
- поиск по имени и пути;
- last opened / last modified;
- переход в проект одним кликом;
- сбор недавних папок из разных окон VS Code.

Почему важно:

Это практически готовая визуальная часть нашего MVP без AI-слоя.

Нужно исследовать:
- механизм получения recent folders;
- формат хранения;
- UI паттерны;
- сортировки;
- last activity;
- multi-window behavior.

---

## 5. Возможности самого Kilo Code

Выяснилось, что Kilo уже имеет глобальную историю локальных sessions и CLI для работы с ней.

Нужно проверить актуальную версию Kilo и подтвердить реальные команды/форматы, но направление выглядит так:

- локальное хранение sessions;
- SQLite / локальная БД;
- поиск сессий;
- работа across workspaces;
- возможность искать прошлые conversations;
- context mentions / Past chats;
- session list/search через CLI.

Это принципиально меняет задачу.

Вместо собственного парсера истории Kilo, возможно, разумнее использовать **официальный CLI/API/внутренний storage Kilo**.

Задача агента на Discovery:
1. найти точные актуальные команды;
2. проверить формат вывода;
3. понять, есть ли JSON mode;
4. понять, возвращается ли workspace path;
5. проверить доступ к title, timestamps, session id;
6. проверить, можно ли получить полный transcript;
7. проверить, можно ли открыть конкретную session;
8. понять, можно ли безопасно вызывать эти команды из VS Code extension.

---

## 6. Chat Searcher

Расширение: **Chat Searcher**

Что интересно:
- индексирует чаты across workspaces;
- использует полнотекстовый поиск;
- применяет BM25;
- умеет фильтровать по workspace;
- позволяет открыть найденный conversation;
- умеет импортировать историю в текущий workspace.

Почему важно:

Это подтверждает нашу исходную гипотезу:

**embeddings для MVP не обязательны.**

Хороший lexical search по title + summary + conversation text может решить большую часть задачи.

Semantic search стоит добавлять только после измерения качества базового поиска.

---

# Что изменилось в концепции Kilo Hub

Изначально мы начали проектировать собственную систему снизу вверх:

**парсер Kilo → индекс → summary → search → API → plugin → UI**

После исследования более логичная гипотеза:

**Kilo Hub = project-centric UI поверх уже существующей истории Kilo и VS Code.**

Основное отличие от найденных решений:

Большинство существующих инструментов отвечают на вопрос:

> «Найди старый разговор».

Kilo Hub должен отвечать:

> «Покажи всю мою AI-работу по проектам и дай быстро продолжить её».

То есть ключевая сущность Kilo Hub — **PROJECT**, а conversations являются его историей.

# MVP после исследования рынка

Первый MVP можно сильно упростить.

## Нужно

### 1. Реестр проектов

Для каждого проекта:
- path;
- display name;
- last activity;
- количество Kilo sessions;
- короткий summary.

### 2. Поиск

По:
- имени проекта;
- path;
- summary.

На первом этапе без embeddings.

### 3. Открытие проекта

Один клик → открыть folder/workspace в VS Code.

### 4. История проекта

По клику можно посмотреть список связанных Kilo sessions.

Это уже может быть второй экран MVP, но индекс должен позволять это сделать.

---

# Что пока НЕ нужно делать

До результатов Discovery не разрабатывать:

- собственный vector DB;
- embeddings pipeline;
- полноценный RAG;
- собственный parser Kilo DB, если есть официальный интерфейс;
- собственный discovery VS Code projects, если существующие API достаточны;
- сложный background service;
- cloud backend;
- синхронизацию между компьютерами;
- переписывание истории Kilo;
- собственную conversation database.

# Hub Index

Минимальная модель данных:

```text
Project
- id
- path
- display_name
- last_activity
- summary
- session_count

Session
- id
- project_id
- title
- created_at
- updated_at
- source
```

На MVP transcript можно не копировать в Hub DB.

Если Kilo предоставляет его по запросу — лучше хранить только ссылки/IDs.

---

# Summary

Summary нужен для проекта, а не обязательно для каждого chat.

Он должен отвечать на вопрос:

> «Что здесь делали?»

Не нужно пересказывать все conversations.

Пример:

> «Разработка LocalMail_Win_Mac_Plus: Outlook/macOS mail integration, communication map, recursive folder scanning, ranking contacts and LLM enrichment.»

---

# Когда считать summary заново

Не на каждый message.

Возможные триггеры:
- появилась новая session;
- существенно изменилась последняя session;
- прошло N новых сообщений;
- пользователь нажал refresh;
- summary отсутствует.

Это нужно уточнить после исследования реальных Kilo timestamps.

Версия 1:

- project name;
- path;
- summary;
- возможно session titles.

Технология:
- обычный full-text;
- SQLite FTS5 или аналог.

Версия 2:

добавить conversation text.

Версия 3:

semantic search / embeddings только при реальной необходимости.

# Hub API и Kilo plugin

Этот слой остаётся полезным, но его не нужно включать в самый первый UI MVP.

Позже Hub должен предоставить формальный API.

Примеры tools:

```text
list_projects()
search_projects(query)
get_project(project_id)
list_project_sessions(project_id)
search_history(query)
open_project(project_id)
```

Для Kilo предпочтителен **Plugin + formal tools**, а не Skill как основной механизм доступа.

Skill может существовать поверх tools и объяснять агенту, когда их использовать.

# Принцип разработки

Перед написанием собственного кода каждый компонент проверять вопросом:

> «Это уже умеет Kilo, VS Code или существующее open-source расширение?»

Если да — переиспользовать или опереться на существующий интерфейс.

Собственный код писать только там, где находится наша уникальная ценность.

---

# Уникальная ценность Kilo Hub

Не ещё один search по чатам.

Не ещё один project switcher.

А объединение двух миров:

**Projects + AI history**

То есть:

> единая карта всей AI-assisted работы пользователя.

Пользователь видит не папки файлов и не отдельные чаты, а **проекты как продолжительные рабочие контексты**.

---

карта коммуникаций

Это и есть основной success criterion MVP.
