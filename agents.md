# Руководство для агентов Kilo Hub

## Цель

Реализовать Step 3 по `req/step3/` и `specs/step3-implementation-plan.md`, сохранив выпущенный Windows baseline Step 2. Порядок: актуализация правил и commit нормативного пакета → discovery → отдельное согласование стека с пользователем → собственная база и фоновая синхронизация → поиск/UI → проверенный VSIX. До согласования стека разрешены исследования и синтетические прототипы, но не production-реализация собственной базы. Step 4 (macOS) отложен до завершения Step 3 и повторного discovery по фактическому результату.

## Обязательный процесс

1. Перед изменением файлов прочитать `specs/step3-implementation-plan.md`, `handoff.md` и относящиеся к задаче требования `req/step3/`. Планы и требования Step 1/2 использовать как исторический baseline там, где Step 3 не задаёт явного изменения.
2. Обновлять план и handoff при изменении этапа, решения, блокера или результата проверки.
3. Хранить реализацию, тесты, документацию, результаты ревью, спецификации и дистрибутивы в выделенных каталогах.
4. Делать минимальное изменение, достаточное для текущего критерия приёмки.
5. Сохранять строго read-only доступ к данным Kilo. Никогда не мигрировать, не создавать, не обновлять и не удалять данные в `kilo.db`.
6. В discovery не читать личную переписку: использовать исходники Kilo, schema-only проверки и синтетические fixtures. После Gate A production Step 3 может читать и локально индексировать только пользовательские text parts по DB-06: без synthetic/ignored, assistant/tool/file/вложений. Не читать файлы проектов; не выводить реальные реплики в инструменты агента, логи, отчёты или fixtures. Исторический metadata-only запрет Step 1 для runtime Step 3 заменён только этим ограниченным scope.
7. Следовать текущему scope `req/step3/`: собственный локальный индекс, автоматическое обновление, поиск и UI разрешены только по последовательным gates. Не добавлять сеть, LLM, telemetry, независимый архив, ручной реестр папок или пользовательское управление базой. Не расширять scope на Step 4 до его gate.
8. Перед отметкой пункта плана как завершённого выполнять относящуюся к нему проверку.
9. Записывать результаты ревью в `reviews/`, а результаты исправлений — в `handoff.md`.
10. Делать коммиты завершённых смысловых этапов. Перед коммитом проверять status, diff и недавнюю историю; добавлять в индекс только целевые файлы.
11. Вести всю проектную документацию на русском языке. Английский допустим только для имён API, идентификаторов, кода, команд и точных технических терминов.
12. После значимых изменений функций, интерфейса, совместимости или ограничений актуализировать пользовательское описание расширения (`docs/extension-description.md`, отображаемое как README во вкладке Details установленного VSIX), краткое `package.json.description` и относящиеся к изменению release notes. Описывать только реально выпускаемые возможности простым языком, без инструкций по внутренней базе. До выпуска проверить включение описания в архив и отображение Details без «No README available»; запись в handoff не заменяет обновление описания.
13. Записывать и мигрировать можно только собственную базу Hub. До любой записи исключить совпадение её пути/идентичности с источником Kilo. Не создавать индексы, triggers или checkpoints в Kilo. Ошибку/частичную сверку не трактовать как удаление; сохранять last-good индекс и координировать writer между окнами.

## Границы каталогов

- `src/`: только production-код расширения.
- `tests/`: автоматические тесты и обезличенные fixtures.
- `docs/`: документация реализации, discovery, проверки и выпуска.
- `specs/`: исполнимые планы и технические спецификации.
- `reviews/`: отчёты ревью и результаты исправлений.
- `dist/`: только сгенерированные VSIX-дистрибутивы; остальные результаты сборки находятся в `build/`.
- `req/`: требования продукта; текущий scope в `req/step3/`, Step 1/2 — baseline, Step 4 — отложенные требования. Исторические решения не переписывать задним числом.

## Критерии качества

- Компиляция TypeScript и lint проходят.
- Unit- и extension-тесты проходят.
- Production bundle не содержит тестовые fixtures и ненужные исходные данные.
- Упакованное расширение открывает источник Kilo строго read-only и поддерживает работающий WAL. Собственная база Hub writable, изолирована от источника и проверена на migration/recovery/multi-window сценариях.
- Поиск и индексация работают на встроенном runtime VS Code без системных Node.js/npm/SQLite/Kilo CLI. Проверки и gates заданы в `req/step3/02-acceptance.md`.
- `npm run package` создаёт версионированный файл в `dist/`.
- Содержимое архива VSIX проверено, пакет установлен в изолированный профиль VS Code.
- `handoff.md` содержит точный путь к артефакту, checksum, известные ограничения и выполненные команды.

## Координация

- Агенты не изменяют файлы за пределами назначенной области.
- Агенты сообщают предположения и доказательства, а не только выводы.
- Если требование противоречит реальности реализации, работа по пункту останавливается, а конфликт записывается в `handoff.md`; молча расширять scope нельзя.
- Параллельные изменения пользователя или других агентов сохраняются, если они прямо не конфликтуют с назначенной задачей.
