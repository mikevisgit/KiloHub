# Vibe Worker Hub / Kilo Hub

## Проблема

При работе в связке **VS Code + Kilo Code** не хватает единой точки, где видна вся прошлая работа.

Проекты физически разложены по разным папкам. Kilo ведёт диалоги внутри этих рабочих контекстов, но со временем становится трудно вспомнить:
- в какой именно папке велась конкретная работа;
- где обсуждалась определённая идея;
- какие проекты вообще когда-либо открывались;
- что происходило в каждом проекте в последний раз.

В OpenCode Desktop сама модель продукта ближе к «вся моя работа в одном месте». Для VS Code + Kilo нужен аналогичный верхний слой.

**Рабочее название:** Vibe Worker Hub / Kilo Hub.

Главная идея: **увидеть всю прошлую работу → быстро найти нужное → продолжить её.**

---

## Что представляет собой Hub

Отдельное **расширение VS Code**, которое становится домашней страницей работы с Kilo.

Оно показывает единый реестр всех проектов/папок, с которыми пользователь работал, и позволяет мгновенно вернуться в нужную.

При этом Hub должен быть не только UI. В перспективе он становится локальным сервисом с формальным API, к которому могут обращаться другие клиенты — в первую очередь сам Kilo.

---

# MVP

На первом этапе не строим большую knowledge/RAG-систему.

Нужно решить одну конкретную боль: **найти нужный проект и открыть его.**

## 1. Реестр проектов

Карточка проекта содержит минимум:
- название папки;
- полный путь;
- дату последней активности;
- короткое summary того, чем занимались в этой папке;
- при необходимости — количество связанных диалогов Kilo.

## 2. Поиск

Единая строка поиска по:
- названию проекта;
- пути;
- тексту summary.

На первом MVP **эмбеддинги не обязательны**.

Если summary достаточно хорошие, обычный полнотекстовый поиск уже позволит находить проекты по смысловым словам: например, «карта коммуникаций», «scheduler», «штатка».

Semantic search через embeddings можно добавить позже.

## 3. Открытие проекта

Клик по карточке проекта:
- открывает соответствующую папку/workspace в VS Code;
- пользователь сразу продолжает работу.

Если технически возможно, позже можно добавить открытие конкретного Kilo-диалога.

# Нулевой этап — Discovery / разведка

До фиксации архитектуры и стека сначала нужно исследовать фактическую среду.

Нельзя проектировать систему исходя из предположений о том, как Kilo и VS Code хранят данные.

## Что исследовать

### Kilo Code

Понять:
- где физически хранится история диалогов;
- формат базы;
- какие сущности там есть;
- как диалог связан с workspace/folder;
- какие timestamps доступны;
- можно ли безопасно читать базу;
- можно ли определить последний диалог/активность проекта;
- есть ли внутренние API;
- есть ли официальный/неофициальный способ открыть конкретный диалог;
- какие интерфейсы доступны плагинам Kilo.

### VS Code

Понять:
- где VS Code хранит список ранее открывавшихся папок/workspaces;
- можно ли получить его через Extension API;
- можно ли определить last activity;
- как программно открыть папку/workspace;
- можно ли переключать workspace без сложных обходных решений.

### Kilo ↔ Hub

Проверить, какой механизм лучше подходит для детерминированного доступа агента к Hub.

Предпочтительная гипотеза:

**Hub API → Kilo plugin → строго описанные tools.**

То есть агент не должен «интерпретировать» инструкции скилла и запускать произвольные скрипты.

Plugin предоставляет формальные инструменты вроде:
- list_projects
- search_projects
- get_project
- search_history
- open_project

Каждый tool детерминированно вызывает API Hub.

### LLM / summary

Проверить:
- каким способом можно вызвать доступную модель для суммаризации;
- можно ли использовать текущую инфраструктуру Kilo;
- где лучше выполнять summary — внутри extension, через Kilo или отдельный локальный сервис;
- когда пересчитывать summary.

---

## Результат нулевого этапа

Короткий технический отчёт в формате:

| Что нужно | Что реально нашли | Доступный интерфейс | Ограничения | Решение |
|---|---|---|---|---|

После этого уже фиксируются архитектура и стек.

# Предварительная архитектурная гипотеза

Пока не решение, а направление, которое нужно подтвердить Discovery.

### 1. VS Code Extension

Отвечает за:
- UI Hub;
- список проектов;
- поиск;
- карточки;
- открытие workspace;
- настройки.

### 2. Локальный индекс Hub

Хранит нормализованное представление:
- project id;
- path;
- timestamps;
- ссылки на Kilo conversations;
- summary;
- служебные метаданные.

Возможные варианты хранения: SQLite или другой простой локальный storage. Выбор — после Discovery.

### 3. Indexer

Собирает данные из:
- VS Code;
- локальной базы Kilo.

Обновляет Hub при появлении новой активности.

### 4. Summarizer

На основе истории Kilo формирует короткое описание проекта.

Важно: summary должно описывать не содержимое файлов вообще, а **что пользователь и агент делали в этом проекте**.

### 5. Hub API

Формальный локальный API поверх индекса.

Он нужен, чтобы Hub не был закрыт внутри UI расширения.

Тогда клиентами Hub смогут стать:
- VS Code Extension;
- Kilo plugin;
- в будущем CLI, OpenCode Desktop или другие агенты.

### 6. Kilo Plugin

Предоставляет агенту детерминированные tools поверх Hub API.

Например пользователь пишет:

> Где мы обсуждали восстановление scheduler после закрытия VS Code?

Kilo вызывает search_history/search_projects и получает конкретные проекты/диалоги.

---

# Skill или Plugin для Kilo

Для доступа к данным основой должен быть **Plugin + tools**, а не skill.

Причина: skill оставляет агенту свободу трактовки инструкций и запуска скриптов.

Для обращения к API Hub нужен более строгий контракт:

**Tool → фиксированный вызов API → структурированный результат.**

Skill при желании можно добавить поверх этого как поведенческий слой: когда искать прошлый контекст, как выбирать результаты, как подмешивать найденное в текущую работу.

Но сам доступ к данным — через tools.

---

# Возможное развитие после MVP

После проверки базового сценария можно постепенно добавить:
- список диалогов внутри проекта;
- переход прямо к конкретному диалогу;
- глобальный поиск по истории всех Kilo conversations;
- embeddings и semantic search;
- гибридный поиск: lexical + semantic + metadata;
- автоматическое обновление summary;
- timeline проекта;
- поиск «где мы обсуждали X?»;
- восстановление контекста проекта перед продолжением работы;
- использование Hub другими агентами и приложениями.

Но ничего из этого не должно усложнять первый MVP.

---

# Предлагаемая последовательность

**0. Discovery** — исследовать реальные базы, API, storage и ограничения.

**1. MVP Hub** — реестр папок + summary + текстовый поиск + открытие проекта.

**2. Hub API** — формализовать доступ к индексу.

**3. Kilo Plugin** — tools для обращения к Hub прямо из диалога.

**4. History Search** — поиск по самим Kilo conversations.

**5. Semantic Search** — embeddings только когда станет понятно, что обычного поиска недостаточно.

---

## Главный принцип

Не строить сразу огромную RAG-систему.

Первая версия должна идеально решать одну бытовую проблему:

**«Я помню, что мы этим занимались, но не помню где. Найди и открой».**
