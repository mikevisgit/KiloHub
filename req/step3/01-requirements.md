# Step 3: локальный поиск и автоматическое обновление Kilo Hub

## 1. Статус и порядок

Документ фиксирует решения пользователя от 21 сентября 2026 года. Текущий результат этапа: ТЗ, не реализация. Обязательная последовательность: **discovery → согласование стека → собственная база и фоновая синхронизация → поиск и UI → проверенный VSIX**.

Стек утверждён пользователем 21 сентября 2026 года после двух циклов discovery: SQLite, встроенный `node:sqlite`, Worker Threads, FTS5 trigram для отбора кандидатов с обязательной точной проверкой подстрок (`instr`). Минимум три Unicode code points в каждом токене; literal-план допустим для случаев, не поддерживаемых MATCH, например NUL. Системный Node.js и сторонний нативный SQLite-модуль пользователю не требуются. Согласование стека не заменяет оставшиеся технические проверки Gate A.

Нормативный baseline: Step 2 / `0.2.3`. Step 3 явно заменяет ограничения metadata-only, отсутствия собственного storage/поиска/фонового обновления только в пределах этого документа. Исторические требования Step 1/2 не переписываются. Строго read-only доступ к Kilo сохраняется без исключений. По решению пользователя правила `agents.md` актуализируются до commit нормативного пакета и последующего discovery; импорт пользовательского текста в production разрешается только после Gate A, личная переписка в discovery не читается.

## 2. Цель и границы

Пользователь видит актуальные папки с Kilo-историей, ищет по именам папок, названиям диалогов и тексту пользовательских реплик, а также может начать работу в выбранной существующей папке. Знания о базе данных, индексировании и синхронизации не требуются.

- Windows x64, локальные поддерживаемые папки; исходный минимум VS Code `1.105.1`. Повышение минимума требует отдельного согласования.
- Не требуются установленные в системе Node.js, npm, SQLite CLI, Kilo CLI, Docker или отдельный сервер.
- Никакой сети, LLM, embeddings, telemetry, ответов ассистента или поиска по содержимому файлов проектов.
- Сохраняются ограничения root/non-archived sessions, исключение UNC, remote/WSL/container и `.code-workspace`/multi-root, существующие правила локальных путей и безопасности действий.
- Нет ручного реестра папок, избранного, создания каталогов, открытия конкретного диалога или просмотра переписки в Hub.

## 3. Собственная база

**DB-01.** Собственная база является восстанавливаемой локальной проекцией Kilo, а не независимым архивом. Kilo остаётся источником истины. Производные данные можно пересоздать без изменения источника.

**DB-02.** Хранить базу в служебном локальном хранилище расширения, вне проектов и отдельно от `kilo.db`. Не добавлять в Git, VSIX или Settings Sync. Точный каталог и реальную область совместного доступа профилей/окон подтвердить discovery; не предполагать, что API VS Code автоматически изолирует профили. Окна, использующие один индекс, должны координировать запись.

**DB-03.** Дополнительного шифрования Hub нет. Принято пользователем: тексты локально читаемы программами с доступом к файлу. Отдельные согласия, предупреждения о копии, мастер настройки и настройки приватности не добавлять. Не обещать защиту, которую реализация не обеспечивает.

**DB-04.** Импортировать всю допустимую историю, постепенно порциями, с ограничением памяти и длительности транзакций. Возобновлять незавершённую подготовку после перезапуска. Нельзя молча ограничить поиск последними тремя диалогами, последними 90 днями или произвольным числом сообщений.

**DB-05.** Целевая проекция: идентификаторы и связи источника, необходимые метаданные папок/диалогов, отобранный пользовательский текст и техническое состояние синхронизации. Не копировать исходные JSON целиком, журнал событий целиком или ненужные поля.

**DB-06.** Отбор пользовательского текста: `message.role=user`, part `type=text`, без `synthetic=true` и `ignored=true`. Вставленный прямо в текст код включается. File/image/tool/reasoning/compaction и прочие нетекстовые parts, ответы ассистента, результаты инструментов и содержимое вложений исключаются. Если автоконтекст смешан с обычным текстом без признаков происхождения, текст сохраняется без эвристического удаления. Не заявлять строгую гарантию авторства человека.

**DB-07.** База Kilo открывается только read-only; никаких migrations, checkpoints, изменения journal mode, triggers или индексов в источнике. Изменения схемы и поисковые структуры разрешены только в базе Hub.

**DB-08.** Различать источники: смена пути Kilo, замена файла, несовместимая схема или сброс журнала не должны смешивать историю разных баз. Способ идентификации и сброса курсоров обосновать discovery.

**DB-09.** Первый adapter ограничен контрактом DB-06 (`message`/`part` обычного чата Kilo в VS Code). Если metadata-only проверка в том же snapshot обнаруживает записи `session_message`/`session_input` у допустимых sessions и их совместимость не доказана, считать источник неподдерживаемым/неоднозначным, сохранить last-good и показать состояние ошибки обновления. Не пропускать эти записи молча, не объявлять индекс полным и не считать неоднозначность удалением. Наличие пустых новых таблиц само по себе не означает несовместимость. Это консервативный отказ, возможны false positives; импорт payload нового формата в этот этап автоматически не добавляется.

## 4. Автоматическое обновление

**SYNC-01.** После запуска расширения автоматически подготавливать/обновлять индекс, даже если панель Hub закрыта. Проверять изменения примерно раз в 10 секунд, пока VS Code работает. Не запускать постоянную отдельную службу после закрытия VS Code. Активацию и выполнение без открытой панели проверить в установленном VSIX.

**SYNC-02.** Тяжёлая сверка выполняется реже, порциями. Конкретный интервал, бюджеты и SLA свежести определить на discovery и записать до реализации. Циклы не перекрываются; длительная обработка не создаёт очередь одинаковых заданий. Фоновое обновление не блокирует Extension Host и Webview.

**SYNC-03.** `session.time_updated` не считать доказательством отсутствия изменений сообщений. Допустима оптимизация через per-session sequence после проверки схемы; обязательна сверка фактического состава sessions и восстановление при пропуске/сбросе курсора. Одного file watcher или durable-журнала недостаточно.

**SYNC-04.** Исправленные реплики заменяют прежний текст. Удалённые messages/parts, удалённые или архивированные sessions исключаются после успешной полной соответствующей сверки. При разархивировании допустимая session импортируется снова. Если у папки не осталось допустимых sessions, она исчезает из истории; текущая доступная папка вместо этого получает временную карточку OPEN-04. Missing-папка с историей сохраняется по правилам Step 2.

**SYNC-05.** Ошибка, частичная выборка, отмена, превышение бюджета или недоступность источника не являются доказательством удаления. При ошибке сохранить последний успешный индекс, предупредить об устаревании, автоматически повторять с увеличением интервала. При несовместимой схеме остановить импорт без повреждения существующего индекса и без записи в Kilo.

**SYNC-06.** Транзакционно фиксировать проекцию вместе с прогрессом/курсорoм. Повторная обработка идемпотентна. Проверить аварийное завершение, два окна, потерю владельца записи, блокировки, недостаток дискового места и восстановление без ручного управления.

**SYNC-07.** Повреждённую производную базу автоматически восстанавливать из источника. Если рабочий индекс ещё доступен, не удалять его заранее: строить замену отдельно и переключать после успешной проверки. Если источник недоступен и индекс нечитаем, показывать понятное состояние недоступности, не выдумывать результаты.

**SYNC-08. Уточнение 22 сентября.** Длительная первоначальная подготовка (в том числе измеренные 259 секунд для теста 10001 диалога) допустима, если выполняется в фоне без блокировки интерфейса. Запаздывание индекса допускается. Оптимизация размеров транзакций, пакетирования и повторной подготовки SQL сама по себе сейчас не требуется.

Обычное обновление обрабатывает новые/изменившиеся диалоги; неизменившиеся реплики не перечитываются и не переиндексируются. Периодическая полная сверка может читать их для обнаружения незажурналированных изменений, но изменяет только обнаруженные различия. Более глубокая сверка допустима при недостаточных сигналах, без безусловного полного перестроения на каждую реплику.

Изменение источника не обнуляет уже завершённую подготовку других диалогов. Согласованная прочитанная версия диалога сохраняется, более свежие изменения обрабатываются следующим проходом; добавление/изменение диалога с ID до ранее сохранённого курсора не теряется. Удаления подтверждаются успешной сверкой. Проверенные завершённые данные доступны поиску во время подготовки с явным признаком неполноты; ошибка или незавершённая запись диалога не публикуется как полная версия. При непрерывном потоке изменений очередь может отставать, но не должна терять сделанную работу.

**DB-10. Проверка целостности.** `quick_check` выполняется перед публикацией нового поколения, при первом открытии поколения в процессе, повторно после замены файла или ошибки чтения. Обычный поиск по уже проверенному неизменённому поколению не повторяет полную проверку. Кэш проверки не отменяет проверки идентичности файла, схемы, владения записью и изоляции от источника Kilo.

## 5. Поиск

**SEARCH-01.** Постоянное поле под строкой «Мои папки с Kilo», над карточками. Placeholder: «Поиск по папкам и диалогам»; доступное имя: «Поиск по папкам, диалогам и вашим сообщениям». Поиск включает названия всех допустимых диалогов, не только трёх отображаемых, и весь импортированный допустимый пользовательский текст. Полные пути не являются поисковым полем.

**SEARCH-02.** Поиск применяется только по Enter. Разделять редактируемый текст и применённый запрос. Ввод сам не меняет выдачу. Крестик очистки или Escape в поле очищает оба значения и сразу показывает весь список. Отправка пустого/пробельного запроса также снимает фильтр. Сохранить глобальное Escape для закрытия видимого tooltip; когда focus в поле, приоритет имеет сброс поиска.

**SEARCH-03.** Нормализация: Unicode NFC, регистронезависимость, `ё=е`, удаление крайних пробелов и разбиение по пробельным символам. Повторные пробелы и повторяющиеся токены не влияют на результат. Каждый токен является буквальной подстрокой, а не regex/SQL/FTS-оператором; кавычки, `*`, `%`, `_` не включают специальный язык запросов.

Минимум для поиска — **3 символа в каждом токене** после нормализации (Unicode code points, не UTF-16 units). Если хотя бы один непустой токен короче, Enter не запускает поиск и не меняет применённый запрос/выдачу; возле поля показать «Введите не менее 3 символов в каждом слове». Короткие токены не игнорировать и не искать полным сканированием. Проверку выполнять и на host до обращения к поисковому индексу. Пустой/пробельный запрос остаётся командой сброса по SEARCH-02; фоновое обновление продолжает использовать предыдущий допустимый применённый запрос.

**SEARCH-04.** Все токены должны встретиться в совокупности полей ОДНОЙ папки. Они могут быть распределены между именем папки, названиями разных её диалогов и разными допустимыми пользовательскими репликами. Каждый отдельный токен должен полностью встретиться внутри одного поля/текстового фрагмента; не создавать ложных совпадений склеиванием границ. Пример: «сайт оплат» находит папку «Сайт», у которой есть реплика «Исправить оплату».

**SEARCH-05.** Порядок найденных папок: совпавшая текущая первая; затем папки, у которых ВСЕ токены есть в собственном имени; затем остальные, у которых все токены покрыты совокупностью имени и названий диалогов; затем папки, для совпадения которых необходимы реплики. Внутри групп сохранить сортировку активности и детерминированные tie-breakers Step 2. Не соответствующую запросу текущую папку скрывать.

**SEARCH-06.** Поиск только фильтрует и ранжирует папки. Содержимое раскрытия не меняется: три последних диалога, прежние действия. Не показывать найденные старые диалоги, цитаты, подсветку реплик, отдельные результаты сообщений или пометку «Совпадение в реплике». Последняя пометка обсуждалась, но затем отменена пользователем.

**SEARCH-07.** При фоновой публикации данных повторять поиск по применённому запросу, не по черновику поля. Старый async-ответ не может перезаписать новый. Сохранять focus, раскрытие и scroll по возможности; если выбранная карточка исчезла, переносить focus в безопасный видимый элемент. Поиск не сохраняется между reload/новым окном; при обычной синхронизации сохраняется.

**SEARCH-08.** При отсутствии совпадений: «Папки не найдены» и «Сбросить поиск». Поиск и плюсик доступны. Пока первичный индекс неполный, показывать «Подготавливаем поиск…»; отрицательный результат не выдаётся за результат полной истории. После завершения поиск автоматически пересчитывается.

## 6. Новая папка

**OPEN-01.** Плюсик в верхней строке справа, на месте рядом с прежним Refresh; сам Refresh удалён. Accessible name и подсказка: «Начать работу в новой папке».

**OPEN-02.** По нажатию открыть штатный диалог выбора одной существующей папки. Отмена не меняет workspace, список или индекс. Выбранную поддерживаемую папку открыть в текущем окне (`vscode.openFolder`, `forceReuseWindow`). Дополнительного подтверждения Hub нет; штатные предупреждения VS Code о несохранённых файлах и доверии сохраняются.

**OPEN-03.** Не создавать каталог и не регистрировать папку в Hub вручную. Без допустимых диалогов Kilo она не появляется в постоянном списке; после появления истории фоновое обновление добавляет её автоматически. Повторный выбор текущей папки допустимо обрабатывать как no-op. Для недопустимого/недоступного пути показать понятную ошибку и оставить текущее окно без смены папки.

**OPEN-04. Текущая папка без истории.** Пока в окне открыта одна доступная поддерживаемая локальная папка без допустимых диалогов Kilo, показывать её временной первой карточкой независимо от того, открыта она плюсиком Hub или средствами VS Code. Это явное исключение из прежнего правила «только папки с Kilo-историей» для представления текущего окна, а не для постоянного индекса. В заголовке обычные имя/монограмма, признак «Вы сейчас здесь» и отдельная текстовая отметка **«Пока без диалогов Kilo»**; не полагаться только на цвет. Не показывать вымышленную дату активности. Полный путь доступен над названием и через ARIA, как у обычной карточки.

При раскрытии внутри только пояснение: **«Эта папка появится в истории после начала общения с Kilo. Информация о диалогах появится здесь автоматически.»** Нет действий, блока «Последние диалоги», пустых разделителей или иных данных. Состояние раскрытия подчиняется общему аккордеону; автоматически раскрывать карточку не требуется.

**OPEN-05. Жизненный цикл временной карточки.** Вычислять её по текущему workspace этого окна, не записывать как папку с историей и не создавать фиктивные sessions/messages. После переключения/закрытия папки карточка исчезает, если реальная история так и не появилась. После reload вычислять её заново; в других окнах без этой текущей папки она не возникает. После синхронизации первого допустимого диалога заменять обычной current-карточкой без дубликата, сохраняя раскрытие/focus по возможности. При активном поиске сохранить SEARCH-05: временная карточка фильтруется только по имени и первая лишь при совпадении; сброс поиска возвращает её наверх.

Отсутствие истории подтверждается успешной проверкой membership для текущей папки, а не отсутствием ещё не импортированных строк. Пока это неизвестно из-за первой подготовки/ошибки источника, не утверждать «Пока без диалогов Kilo»: использовать общие loading/stale состояния и last-good данные. Не создавать временную карточку для unsupported/missing workspace; при подтверждённой потере доступности временная карточка снимается, не превращаясь в постоянную missing-историю.

## 7. Простой интерфейс

**UI-01.** Сохранить дизайн, темы, монограммы, аккордеон, current/missing, доступность и адаптивность Step 2. На 260/320/400 CSSpx и 200% zoom нет горизонтального переполнения.

**UI-02.** Значок `ⓘ` сохраняется, его подсказка возвращается: «Здесь собраны папки, в которых вы работали с Kilo. Чтобы вернуться к работе, выберите папку и откройте её.»

**UI-03.** Ровно три категории tooltip: пояснение `ⓘ`, пояснение плюсика, полный путь при hover текста имени папки. У остальных элементов нет tooltip, в том числе native `title`. Path не появляется на всей плашке или её focus; ARIA полного пути сохраняется. Для `ⓘ` и плюсика разрешён показ по hover/focus. Все popup pointer-pass-through, немедленно скрываются при попадании указателя на их геометрию и по Escape, не удерживаются повторно над источником до завершения interaction.

**UI-04.** Никаких пользовательских настроек базы, интервала, шифрования, команд очистки/пересоздания/паузы/возобновления или ручного Refresh. Не добавлять технический прогресс и постоянные уведомления «Данные обновлены». Старую публичную команду `kiloHub.refresh` не оставлять в качестве необходимого пользовательского сценария; судьбу её идентификатора оценить отдельно при реализации, не вводя новый UI.

**UI-05.** Видимые состояния: «Подготавливаем поиск…» во время неполной подготовки; при устойчивом сбое «Не удалось обновить данные. Повторим автоматически». Технические причины доступны в Output без реплик/секретов. Кратковременные busy-состояния не должны вызывать всплывающие ошибки. Порог устойчивого сбоя определить в техническом плане.

## 8. Описание страницы расширения

**DOC-01.** Включить в Step 3 пользовательское описание для вкладки Details страницы Kilo Hub в VS Code вместо «No README available». Канонический текст хранить в `docs/extension-description.md`; при упаковке передавать его как README средствами packager (например, `--readme-path`) и проверять фактическое назначение README в VSIX. Один источник текста, без вручную поддерживаемой второй копии.

**DOC-02.** Описание на русском, простым языком: назначение Hub, где открыть панель, как вернуться к папке, как искать (Enter, крестик/Escape), что ищется, плюсик и открытие существующей папки в этом окне, временная карточка без диалогов, автоматическое обновление и основные ограничения. Указать поддерживаемые ОС/VS Code/Kilo и отсутствие необходимости отдельно устанавливать Node.js. Не описывать внутреннюю схему, курсоры, управление индексом и прочие технические детали. Не добавлять отдельного согласия или предупреждения о копировании реплик. Не выдавать будущие возможности (включая macOS до её выпуска) за реализованные.

**DOC-03.** Актуализировать короткое `package.json.description` под фактические функции Step 3; release notes не заменяют описание Details. Ссылки и изображения, если используются, должны корректно отображаться в установленном VSIX, не содержать личных данных и не требовать загрузки внешних ресурсов для чтения основного описания.

**DOC-04.** После каждого значимого изменения пользовательских возможностей, интерфейса, требований к среде или ограничений обновлять описание, краткий manifest description и release notes в затронутой части. Проверять соответствие одному выпускаемому artifact; не описывать ещё не включённые функции. Это постоянное правило проекта, не разовая задача Step 3.

## 9. Защита и проверка

**SEC-01.** Пользовательские строки считаются недоверенными: параметризованные SQL, безопасный DOM, CSP, ограниченные сообщения host/Webview. Реплики остаются в host/worker и не пересылаются в Webview: UI получает папки, три названия диалогов и состояния, но не весь поисковый корпус.

**SEC-02.** Без реплик в логах, скриншотах, fixtures, отчётах, telemetry и VSIX. Тесты используют синтетическую историю. Discovery не читает личную переписку: upstream-код, schema-only проверки при разрешении, синтетические базы.

**SEC-03.** При сохранении собственного индекса строго развести writable Hub connection и read-only Kilo connection. Изменение path/config не должно направить миграцию Hub в источник. Проверить совпадение путей и доступные на Windows способы идентичности файлов до любой записи.
