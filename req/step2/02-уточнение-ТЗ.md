# Step 2 — уточнение ТЗ

## Назначение

Документ фиксирует последовательные решения пользователя по изменению дизайна Kilo Hub. Каждый ответ записывается до следующего вопроса и имеет приоритет над более ранней формулировкой канонического ТЗ Step 2.

## Правила ведения

- Один вопрос за один раз.
- Вопрос касается одного конкретного визуального или UX-решения.
- Принятый ответ записывается дословно по смыслу, без скрытого расширения scope.
- Если решение отменяет существующее требование, указывается заменяемый раздел канонического ТЗ.
- Нереализованные идеи не считаются принятыми требованиями.
- Открытие конкретного Kilo-диалога не добавляется: публичного local-session API Kilo Code 7.7.5 нет, пользователь отказался от upstream-изменения.

## Зафиксированная основа до уточнений

- Выбран один дизайн: «Монограммы».
- Представление Step 2 реализуется как `WebviewView` в существующем контейнере Kilo Hub.
- Текущая папка первая и помечена «Вы сейчас здесь».
- Диалоги остаются пассивным текстом; показываются до трёх последних.
- Источник данных остаётся metadata-only и read-only.
- Поиск, ручной реестр, telemetry, сеть, LLM и открытие диалога не добавляются.

## Принятые уточнения

Последнее решение **УТЗ-10** приоритетно для всех активных документов и макетов. Формулировки УТЗ-05 и УТЗ-09 о прежних owners и показе по focus сохранены как история и не действуют там, где противоречат УТЗ-10. Геометрическое скрытие и `pointer-events:none` из УТЗ-09 сохраняются.

### УТЗ-01. Верх панели

**Вопрос:** оставить две строки «Kilo Hub» и «Мои папки с Kilo» либо сократить шапку?

**Решение пользователя:** оставить обе строки.

**Следствие:** каноническое ТЗ и выбранный макет уже соответствуют решению; визуальная структура header/intro не меняется.

### УТЗ-02. Статус дизайна и правило дальнейших вопросов

**Решение пользователя:** дизайн полностью принят.

Дальнейшие вопросы задаются только в одном из трёх случаев:

1. Решение физически или технически не помещается в ограничения VS Code/Webview.
2. Требование существенно меняет ранее принятую концепцию Kilo Hub.
3. Требование драматически усложняет реализацию или поддержку.

Вкусовые варианты, уже определённые каноническим ТЗ, повторно не согласовываются.

### УТЗ-03. Визуальная приёмка макетов

**Решение пользователя:** пользователь уже просмотрел макеты, они ему нравятся и визуально приняты.

**Следствие:** композиция «Монограммы», визуальная иерархия, палитра, размеры, интервалы и общий характер макета не выносятся на повторное обсуждение. Статические макеты считаются утверждённым визуальным эталоном; вопросы возможны только по технической реализуемости в реальном VS Code и перечисленным в УТЗ-02 исключениям.

### УТЗ-04. Удаление строки `Kilo Folders`

**Решение пользователя:** строку `Kilo Folders` удалить.

Скрыть нативную строку заголовка `WebviewView` поддерживаемым API VS Code нельзя, поэтому решение реализуется без визуального изменения принятой двухстрочной структуры:

1. Нативное имя view меняется с `Kilo Folders` на `Kilo Hub`.
2. Дублирующая DOM-строка `Kilo Hub` внутри Webview удаляется.
3. DOM-строка `Мои папки с Kilo` сохраняется вместе с info и refresh.

Итоговый верх панели содержит ровно две видимые строки:

1. нативный заголовок VS Code `Kilo Hub`;
2. строку Webview `Мои папки с Kilo`.

УТЗ-01 про сохранение обеих строк трактуется как сохранение этих двух видимых смысловых уровней, а не как требование рисовать отдельный DOM-дубликат `Kilo Hub`.

### УТЗ-05. Доступное поведение tooltip

**Решение пользователя:** согласован рекомендуемый доступный вариант.

Внешний вид карточек и содержание подсказок сохраняются, но поведение заменяет прежние hover-only правила канонического ТЗ:

1. Tooltip показывается при наведении мыши и при keyboard focus источника.
2. Tooltip не исчезает при переходе курсора с источника на сам popup и остаётся видимым, пока пользователь его читает.
3. Popup располагается внутри доступной области Webview, чтобы полный путь и пояснения не обрезались границей панели.
4. Escape закрывает tooltip; уход мыши и потеря keyboard focus закрывают его после завершения взаимодействия с источником/popup.
5. Полный путь и пояснения имеют устойчивую ARIA-связь с источником; одинаковые имена папок различимы без мыши.
6. Визуальная композиция «Монограммы» не меняется.

УТЗ-05 отменяет противоречащие правила строк 60–72 канонического ТЗ: hover-only, немедленное скрытие при входе в popup, `pointer-events:none` и отказ от viewport-fit.

### УТЗ-06. Контраст и пользовательские темы VS Code

**Решение пользователя:** адаптироваться к теме; рекомендуемый вариант принят.

1. Обязательная проверка контраста выполняется на встроенных dark, light, dark high-contrast и light high-contrast темах VS Code.
2. В сторонних пользовательских темах интерфейс использует семантические `--vscode-*` tokens и считается best effort.
3. Для монограмм при недостаточном контрасте автоматически выбирается более читаемый чёрный или белый цвет инициалов по уже заданному алгоритму.
4. Расширение не навязывает собственную полную тему и не обещает соответствие 4,5:1 для любого произвольного сочетания цветов стороннего theme extension.
5. Forced colors и high-contrast режимы сохраняют системные цвета и отдельные проверки доступности.

УТЗ-06 уточняет требования канонического ТЗ о «произвольных пользовательских темах»: совместимость обязательна, абсолютная гарантия контраста вне проверяемого набора — нет.

### УТЗ-07. Проверка готового Webview и повторные ревью

**Решение пользователя:** финальную визуальную проверку установленного окна выполняет пользователь; агент должен проводить ревью несколько раз, пока всё не будет исправлено.

Обязательный процесс:

1. Логика, host/Webview protocol, DOM-контракты, accessibility helpers, CSP, packaging и regressions покрываются автоматическими тестами настолько, насколько позволяет публичный API VS Code.
2. Для реального установленного VSIX готовится ручной чек-лист: клавиатура, tooltip, screen reader semantics, 260/320/400 px, zoom 200%, dark/light/high-contrast, смена темы, accordion, быстрые нажатия, scroll compensation, refresh/error/missing/current и три folder actions.
3. Пользователь выполняет финальную визуальную проверку окна. До его результата нельзя заявлять, что pixel-level рендер и субъективное визуальное качество приняты.
4. Агент проводит независимые ревью требований, Webview security/CSP, accessibility/keyboard, архитектуры/refresh protocol, tests и package contents.
5. После исправлений ревью повторяются. Цикл продолжается, пока не останется нерешённых findings.
6. Физические ограничения VS Code допускаются только как явно доказанные и записанные ограничения с безопасным поведением; они не скрываются под формулировкой «не проверено».
7. Итоговые отчёты и результаты исправлений хранятся в `reviews/`, команды и evidence — в `handoff.md` и документации проверки.

Полная внешняя GUI/CDP-автоматизация не является обязательной: она непропорционально хрупка к внутреннему DOM самого VS Code. Это не отменяет component tests и обязательную ручную проверку пользователем.

### УТЗ-08. Производительность и будущее собственное хранилище

**Решение пользователя:** числовой performance-порог пока не задавать; в будущем продукт планируется перевести на собственное хранилище.

Следствия для Step 2:

1. Требование Step 1 об обработке 1000 sessions без заметной блокировки сохраняется как regression check, но не получает нового числового release gate.
2. Отсутствие точного порога не блокирует реализацию утверждённого Webview-дизайна.
3. Step 2 продолжает использовать существующий metadata-only read-only adapter к Kilo SQLite.
4. Собственное хранилище, миграция данных, schema нового storage и синхронизация не входят в Step 2.
5. Переход на собственное хранилище оформляется отдельным будущим этапом и новым нормативным ТЗ.

### УТЗ-09. Сокращение и немедленное скрытие tooltip

**Решение пользователя:** убрать лишние подсказки и не позволять popup перекрывать содержимое под курсором.

1. Заголовок `Последние диалоги` не является tooltip owner и не получает отдельный `tabindex` или `aria-describedby`.
2. Названия диалогов не имеют pointer-tooltip. Видимый title остаётся однострочным с ellipsis, а полный title присутствует ровно один раз в accessibility tree через visually-hidden span.
3. Остальные подсказки сохраняются для полного пути, info, refresh и действий папки, включая keyboard focus и устойчивую ARIA-связь.
4. Popup не перехватывает pointer events. Если координаты `pointermove` попадают внутрь или на границу прямоугольника видимого popup, он скрывается немедленно в том же событии.
5. После геометрического скрытия текущий owner подавлен до настоящего завершения взаимодействия с ним; движение над лежащим под popup owner не показывает ту же подсказку повторно.

УТЗ-09 имеет приоритет над пунктами УТЗ-05 об удержании popup при наведении на него и над прежним списком owners. Доступность оставшихся интерактивных источников по keyboard focus не отменяется.

### УТЗ-10. Только полный путь по hover текста имени

**Решение пользователя:** удалить все tooltip, кроме полного пути при наведении именно на текст `.folder-name`, а не на всю `.folder-head`.

1. Единственный visual tooltip owner и anchor полного пути: текст `.folder-name`, одинаково в collapsed/expanded, current/missing состояниях. Свободное место строки имени и остальная площадь `.folder-head` не расширяют hover-зону текста.
2. Hover/focus info, refresh, actions, head вне текста имени, date, mono, history и conversations не показывает popup. Focus любого элемента, включая head, сам по себе не показывает и не удерживает popup. Нативные `title`-подсказки также не допускаются.
3. Полный path постоянно доступен через устойчивый `aria-describedby` кнопки `.folder-head`, независимо от видимости popup. `.folder-name` не получает отдельный Tab-stop; keyboard activation и видимый focus кнопки head сохраняются. Доступные имена info/refresh/actions и полный title диалога в accessibility tree сохраняются без визуальных подсказок.
4. Hover текста имени показывает полный path немедленно. Уход с текста скрывает popup немедленно даже при focus на head, без grace. `Escape` и попадание `pointermove` внутрь или на границу popup скрывают его в том же событии; повторный показ подавлен до настоящего leave/reentry текста имени. Focus не снимает и не удерживает подавление.
5. Сохраняется УТЗ-09: popup имеет `pointer-events:none`, не перехватывает клики, не содержит интерактивных потомков и не входит в Tab-порядок. Геометрическое скрытие работает и при owner под popup. Стабильный ARIA-текст и viewport-позиционирование сохраняются.
6. Текущий package gate: `0.2.3`, артефакт `dist/kilo-hub-0.2.3-win32-x64.vsix`. Иконка страницы расширения в manifest: PNG `resources/kilo-hub.png`; иконка Activity Bar остаётся `resources/hub.svg` без изменения. Обе входят в exact package allow-list и проверку hashes.

УТЗ-10 заменяет противоречащие tooltip-контракты УТЗ-05/09, канона, size spec, matrix и manual checklist. Старые макеты и offline-проверки не являются доказательством соответствия УТЗ-10. Фиксация требования не означает прохождения production/package/manual проверок `0.2.3`.

## Открытый вопрос

### ОУ-01. Поведение tooltip и доступность — закрыт

Feasibility-аудит выявил технический конфликт в каноническом ТЗ, строки 60–72:

- tooltip показывается только мышью;
- при уходе с источника исчезает немедленно;
- при попадании курсора в прямоугольник popup также исчезает;
- с клавиатуры полный путь и пояснения недоступны;
- popup шириной до 330 px может обрезаться границей узкой Webview-панели, хотя полный путь является единственным различием папок с одинаковым именем.

На момент аудита прежнее правило не соответствовало WCAG 2.2 AA для hover content и не гарантировало доступ к полному пути. Это историческое обоснование, а не открытый вопрос или действующий контракт.

Статус: первоначально закрыт решением УТЗ-05; действующее поведение заменено УТЗ-10. Полный путь доступен без мыши через ARIA, но соответствие WCAG для hover content этим решением не заявляется.

## Результат feasibility-аудита

### Подтверждено без дополнительных вопросов

- Выбранный дизайн «Монограммы» реализуем через VS Code `WebviewView` версии 1.105.1+.
- SQLite adapter, read-only worker, domain projection, path safety и три существующие команды сохраняются как backend.
- Webview получает только минимальный DTO; прямого доступа к БД нет.
- Production использует строгую CSP, локальные browser assets и runtime-проверку входящих сообщений.
- Demo-код является behavioral reference, а не готовым production bundle.
- Нативная toolbar-команда refresh удаляется, чтобы не дублировать утверждённую кнопку Webview.
- По УТЗ-10 только hover текста `.folder-name` немедленно показывает полный path; focus не показывает popup, grace отсутствует. Полный path постоянно связан с кнопкой head через ARIA.
- Reduced motion учитывает и `body.vscode-reduce-motion`, и `prefers-reduced-motion`.
- Snapshot хранится в host; раскрытый ID и scroll state восстанавливаются через Webview state без лишнего чтения БД.
- Полностью автоматическая проверка DOM установленного Webview через публичный VS Code API невозможна; нужны component tests и ручной installed-VSIX протокол.

### Технические вопросы, которые допускаются правилом УТЗ-02

1. **Tooltip и доступность:** первоначальное решение УТЗ-05 заменено приоритетным УТЗ-10.
2. **Три строки в шапке:** закрыто решением УТЗ-04; `Kilo Folders` удаляется как текст через переименование нативного view, DOM-дубликат `Kilo Hub` не создаётся.
3. **Контраст пользовательских тем:** закрыто решением УТЗ-06; фиксированный проверяемый набор плюс best-effort fallback.
4. **Ручная UI-приёмка:** закрыто процессом УТЗ-07; автоматические проверки дополняются повторными ревью и финальным пользовательским чек-листом.
5. **Performance gate:** числовой порог отложен решением УТЗ-08; сохраняется существующий regression check без нового блокирующего SLA.

Вопросы задаются строго по одному и только после закрытия предыдущего. По результатам текущего feasibility-аудита обязательных открытых вопросов больше нет.
